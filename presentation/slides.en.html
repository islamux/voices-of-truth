Opening · the gap

What problem does this product build a solution for?

discoverability

No unified index

How does one find a prominent scholar known among his audience? Who searches for a preacher fluent in Arabic in Egypt? Knowledge is scattered across countries, specializations, and languages with no single path.

arabic-search

Arabic search, programmatically

Diacritics (مُحَمَّد), hamzas (أ إ آ ٱ), yaa (ى/ي), and taa marbuta (ة/ه) — all of them make an exact match fail to pair 'محمد' with 'مُحَمَّد'.

i18n

A bilingual audience

Arabic (full RTL) and English (LTR), with one correct direction kept in every layout and flex arrangement.

structured not free text

Structured data, not free text

A scholar has a country, a specialization, languages, and links — entities with fixed dimensions, and that is what makes server-side filtering possible instead of floating search.

Thesis · the governing idea

The server decides; the client interacts

Every "fact" — normalization, validation, filtering, pagination — is settled before leaving the server. What reaches the browser is a finished result, and its only behavior is rewriting the URL.

src/app/[locale]/page.tsx:24-48 (validation, filtering, and pagination on the server)

Why is this right here?

The content is static and structured, so server-side filtering is cheaper and consistent with pre-generation; and URL-as-state gives back/undo for free.

The decision journey · the deepest decision

ADR-009: why we dropped next-themes

Cause

A technical decision, not a stylistic one

next-themes 0.4.6 injects <script> inside the provider tree, while React 19 / Next 16 rejects that pattern with a console error. The library has been stale since 2024.

Decision

A custom theme provider

ThemeProvider + useTheme in src/lib/theme.tsx (~70 lines), and the script moves to the server before hydration.

Reflection

Zero dependency

No script errors, no flash, no external bundle. This is the condition that made the full Hydration section of this deck a must.

Hydration 1/4 · the concept

What happens between the React server and the browser?

1 · Server renderbuilds the tree; sees no window, no localStorage
2 · HTML responsearrives and renders before the JavaScript is complete
3 · First client rendermust produce the same initial tree, literally
4 · Hydrationattaching React to the existing shell and wiring events — not CSR from an empty DOM
5 · EffectsuseEffect runs after commit: reads the browser, updates state later
6 · Mismatcha difference before hydration → warning / error / DOM reset

The central question for the team: "What if the client's first render differs from the server tree?" — the answer is on the next slide, with a real case from this project.

Hydration 2/4 · the error story

The error that made this section mandatory

The wrong root

A read during the first render

Never touch "window" or "localStorage" in the component body during the first render — the server has neither.

The wrong mechanism

A rejected example

const theme = localStorage.getItem('theme') // ✗ return theme === 'dark' ? <Moon /> : <Sun />

Server: "system". First client render: "dark". Two different trees.

The documented outcome

Different rendering until hydration

A Hydration warning/error, a possible DOM rebuild or unexpected behavior — docs/fix-hydration-error.md:5-10.

Hydration 4/4 · the decisive distinction

mismatch ≠ an update after commit

✗ mismatch

A difference in the initial trees

Happens at Hydration when the client's first render differs from the server tree. Prevention: a mount guard + a read after commit.

✓ post-commit update

Expected and correct

After hydration completes, ThemeToggle flips from a placeholder to a real icon in response to the browser's system — a state updated after commit, not an initial difference.

The ruling rule

If the first render matches the server tree, any later update via useEffect/external cues is an understood update, not an error — and that is the name the presenter must give the team.

Trade-offs · what did we gain and what did we pay?

A decision, then its price — both in front of you

Gained

A back-button-friendly architecture

URL-state gives back/undo/share for free; pre-declaration pins paths without request-time computation; a zero-dependency theme; and pure functions tested in isolation.

Paid

A fixed scaling cost

Data in TS files: adding a scholar = a code change + a rebuild; O(n) filtering per request (fine at 26, suspicious at thousands); no CMS, no non-technical editing.

When to revisit

A stated threshold

When the scholar count approaches the hundreds, or an editor wants to change a record from a UI — at that point a DB or CMS becomes a necessity, not a luxury.

docs/adr.md (the decisions) · docs/improvement-plan.md:397-413 (the future CMS)

Known limits · credibility before praise

What is not solved yet — a stage decision, not an oversight

No full PWA

A manifest alone is not enough

manifest.ts exists (name/icon/start_url), but there is no service worker, no install, and no real offline mode. Don't claim "installable" or "offline".

No data/identity

A deliberately static directory

No database, no auth, no API — zero data-ingress surfaces; and the scale pain at hundreds has a planned path.

No E2E

Core tests, not shell tests

No components, no hooks, no E2E; no measured coverage. Plan 5.1-5.2 charts the route to 70%.

No measurement/monitoring

A structure ready without numbers

No official Lighthouse, no Sentry, no LogRocket — fixed benefits with no numeric proof yet.

Roadmap · by risk, not by liking

Priority by compounded risk

P0 — data risk

Split the data into a DB/CMS with a schema for the pending scholars-db.json, plus a migration script and an integration test (protect trust before any feature).

P1 — interaction risk

Component tests (ThemeToggle/FilterBar) + hooks, with a clear path to 70% measured coverage.

P2 — growth risk

Explicit measurement of filterScholars above 1,000 scholars, then an index/structure decision by number, not by guesswork.

P3 — monitoring and security

Production error capture (ideally Sentry) + automated CSP checks in the build, and before all that a real production domain.
